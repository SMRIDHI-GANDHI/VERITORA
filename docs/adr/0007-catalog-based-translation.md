# ADR 0007 — Catalog-based explanation translation
Status: Accepted
Context: FR-15/FR-TR require translated explanations for fixed recommendation/factor text and clause wording help while preserving originals, showing translation confidence/uncertainty, and never translating/fabricating external verification facts. The product must remain safe and deterministic when `LLM_ENABLED=false` and must not introduce runtime dependency on third-party translation APIs.

Decision:
- Use local JSON catalogs (`app/config/i18n/explanations_<lang>.json`, currently `en`, `hi`) as the source of translated strings for known recommendation codes, risk-factor codes, and disclaimers. Catalogs are loaded lazily and cached (`lru_cache`) per language.
- Translation endpoints/services return both translated text and originals (`text_original` / `explanation_original`) plus explicit metadata: `translation` with `source_language`, `target_language`, `provider` (`catalog` or `original`), `confidence`, `uncertain`, and `note` (e.g. "Machine-translated, may be inaccurate." when missing). Unsupported/unknown languages fall back to `en`; unknown keys fall back to original English with low-confidence/uncertain markers for non-English requests.
- Wording explanations (`/explanations/wording`) are rule-based over the provided (untrusted) text and return `method: rule_based` findings with no external translation/provider (`provider: none`) and no verdicts or external verification claims. External/user-submitted text is treated as data, not instructions.
- No LLM or external translation service is called for catalog translation; this keeps behavior deterministic, offline-capable in degraded environments, and free of data egress/consent concerns for these fixed strings.

Consequences: Coverage is limited to cataloged codes/languages; adding a language or new factor/recommendation requires catalog updates and review for accuracy/neutrality. Because translations are fixed strings (not runtime MT of arbitrary evidence), risk of hallucinating verification facts is avoided, but newly introduced codes may temporarily render as uncertain/fallback until catalogued. Any future runtime MT for arbitrary text would require explicit consent/disclosure, safety review, and a new ADR/contract update.

Alternatives considered: (1) LLM/runtime machine translation — rejected for fixed explanations due to nondeterminism, possible factual drift, cost/latency, and data-handling/consent requirements. (2) Third-party translation API — rejected for dependency/availability/egress and the need to translate only controlled internal strings. (3) Store translations only in frontend i18n — rejected because API clients/tests need consistent, auditable translated explanation payloads and preserved originals/metadata from the backend.
