# ADR 0003 — Grounded chatbot: evidence pack, degraded mode and credential refusal
Status: Accepted
Context: FR-CH-1 requires chat answers grounded in stored analysis and approved sources, citing evidence, separating fact / user report / AI interpretation, refusing certainty when data is missing, and never collecting passwords or OTPs. FR-CH-2 requires the chatbot to work in a degraded (templated) mode when the LLM is disabled. `docs/08-SECURITY-PRIVACY.md` requires prompt-injection defence: external content is data, never concatenated into system instructions, with schema-validated output and no LLM tool access.

Decision:
- **Evidence pack as the only source of truth.** Every answer is built from a list of evidence entries with stable ids (`ev:analysis`, `ev:factor:<CODE>`, `ev:check:<TYPE>`, `ev:community`, `ev:recommendation:<CODE>`, `ev:unknown`, `ev:resource:<ID>`). Citations are filtered to ids that exist in the pack, so a model can never cite invented evidence.
- **Two responders behind one contract.** With `LLM_ENABLED=false` (the default) a deterministic rule-based responder answers from the stored analysis, the rule engine's recommendations and the configured cyber resources. With an LLM enabled, the model receives a strict system preamble plus a delimited evidence pack, and its JSON output is validated (`answer`, `citations[]`, `statement_types[]`). Any failure — transport error, non-JSON output, empty answer, unknown citation — falls back to the rule-based responder. The API response shape does not depend on which path ran (`mode` reports it).
- **Missing evidence is stated explicitly.** Checks that were expected but never performed are added to the pack with status `not_checked`, so the responder says "I cannot tell you about them" rather than implying verification happened. Only moderator-approved community reports contribute a `user_report` statement, and raw reporter descriptions are never included.
- **Credential refusal before persistence.** A message containing credential material (password, OTP, PIN, banking details, unredacted ID number) is detected before it reaches the database: nothing is written, `stored` is `false`, `user_message` is `null`, and the user receives a warning telling them not to share such data and to rotate anything already shared.
- **Injection defence in depth.** Instruction-like content is stripped from the user's text before storage, the prompt declares both the evidence pack and the user question to be data, and the rule-based responder never reads free-form instructions. The LLM has no tools and no network access.
- **`httpx` promoted to a runtime dependency.** The TRD already lists `httpx` as the project's HTTP client; the optional LLM client uses it with a short timeout and a capped response size. The API key is never logged.

Consequences: Answers are reproducible and auditable in degraded mode, and the LLM can only add phrasing, never facts. Citation ids are part of the public contract, so new evidence kinds require a new `ev:` prefix and a contract update. Chat sessions add two tables (`chat_sessions`, `chat_messages`, migration 0009). The LLM provider is limited to OpenAI-compatible `/v1/chat/completions` endpoints; other providers need a new adapter behind `LLMClient`.

Alternatives considered: (1) Free-form chat without an evidence pack — rejected, it invites invented company facts. (2) Retrieval from the raw database at answer time — rejected, it would leak non-approved reports and raw reporter text into the prompt. (3) Persisting credential-bearing messages and redacting later — rejected, the data would still be retained, which FR-CH-1 and the privacy rules forbid. (4) Streaming token-by-token answers — rejected for now, because citations and statement labels must be validated as a whole before anything is shown or stored.
